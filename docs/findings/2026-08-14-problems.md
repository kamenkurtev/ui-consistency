# Problems found — 2026-08-14

Running notes. One entry per problem, kept short. The direction at the bottom is
what we have agreed so far, not a design.

---

## The root problems — why this plugin was started

### P0 — The agent builds a whole flow badly

Given one task — *build this flow of pages and components* — the agent does it
badly, and the user then repairs it prompt by prompt, component by component,
page by page. Everything else in this list is a patch applied downstream of
this.

What goes wrong, from the inside of doing it:

- No vocabulary is fixed before writing. Components are chosen per file, from
  what looks reasonable inside that file.
- No screen is treated as the canon for its kind unless somebody says so, and
  even then one screen is read rather than the pattern across several.
- Prop-level conventions — which variant, which spacing, which wrapper carries
  the scroll — are never decided, so each page gets its own plausible answer.
- Across many files the early decisions fade from context; page eight no longer
  matches page two and the drift compounds silently.
- The target being optimised is "this file renders and looks right on its own".
  Each page is defensible alone; the set is inconsistent.
- Verification at the end is per file (tests pass), never across the set.

### P0b — The agent cannot hold one pattern across thirty pages

Here the pattern is already decided — put this holder around these components,
wire it to each page's own logic — and it must be applied to ~30 existing pages.
Some come out right, others do not, and the user goes through them one at a time.

- Each file is edited in its own turn, with the pattern **recalled** rather than
  re-read from a fixed source. Every recollection differs slightly.
- The wiring genuinely differs per page, and adapting the wiring is where the
  *shape* silently changes too.
- There is no mechanical definition of done for a page. "Looks plausible" is
  satisfied by every deviation as well.
- Long batches degrade: later files get less attention, and the pattern drifts
  toward the most recently seen example rather than the canonical one.
- Nothing compares page 27 with page 1. 22 of 30 correct looks exactly like
  30 of 30 until a person opens them.

### P0c — What the mistakes are: layout, choice, configuration

- **Layout arrangement** — the order and nesting the other pages share is not
  reproduced, because it was never extracted from them.
- **Wrong component** where a right one exists.
- **Right component, written raw.** A `<Button>` with no props, while every
  other page writes that button with a particular variant, size and placement.
  The component is correct and the *usage* is not.

Why the check does not happen: writing from knowledge is cheap, reading three
sibling pages first costs calls and context, and nothing forces it. When a
neighbouring file is read, it is read for the thing being added, not for the
conventions around it. A bare `<Button>` looks complete.

`src/sources/usage.ts` already computes this — and delivers it after the write,
as text.

## How the work actually runs

1. Paste a Jira link and say what has to be done.
2. Run the **requirements agent**: own instructions, the brainstorming skill, a
   Jira connection. It writes the plan, attaches artefacts, creates the story.
3. Run the **development agent**: parts of the superpowers skills, the team's own
   skills, code review, receiving code review.
4. Claude develops. At this point the work is expected to be *done*.
5. Tests and an environment are started. **The user opens the page and compares
   it with the other pages by eye.**
6. There are many mistakes. The user corrects them one element at a time: *look
   at this page for reference; there we use this component; this button has
   these settings.*

Step 6 is where the time and the tokens go. Nothing in the plugin takes part in
steps 1–3, where the decisions that cause step 6 are made.

## What is wrong with the plugin as built

### P1 — The checks carry MUI's vocabulary

`src/checks/reuse.ts:17-28, 44-57` and `src/sources/archetype.ts:14-16` hardcode
`Button`, `Link`, `TextField`, `Select`, `MenuItem`, `Table*`, `Dialog`,
`Modal`, `Drawer`, `DataGrid`, `Checkbox`…

Every team names its components its own way, and every framework has its own
pseudo-HTML elements — `<ion-input>`, `<app-button>`, `<v-btn>`, `<mat-select>`,
`<sl-dialog>`. A project whose input is `Textbox` and whose table is `DsTable`
matches none of it.

The result is **silence, not a wrong finding** — and silence is
indistinguishable from a clean result.

### P2 — Foreign component names inside the user's own file

`src/cli/init.ts:60-61` writes `<PageLayout>`, `<PageHeader>`, `<Content>`,
`<ActionGrid>`, `<Grid>` into `.claude/ui-consistency/` as examples, with
nothing saying they are examples.

### P3 — The layer machinery answers one narrow question

Detection, the graph, the chain and the inventory all serve: *is this symbol
available from a nearer layer?* Only 2 of the 6 deterministic checks read
imports. Without a wrapping layer the question has no answer, however wrong the
UI is.

### P4 — Findings are text the agent may skip

The hook returns `additionalContext` on `PostToolUse`. In the monorepo the
findings were not acted on. The advice was not wrong — it was ignored.

### P5 — Nothing is measured where it matters

No data from the monorepo: whether a knowledge base existed, which checks fire
with a real core layer, how often findings are ignored. Every measurement so far
comes from repositories with no wrapping layer.

### P6 — When and how it starts is Claude-Code-only, and per edit

Today: a 776 KB Node bundle on `PostToolUse`, with Claude Code's event name and
response shape, on every write.

Reference — how `superpowers` is organised:

- The payload is `skills/` — 14 directories of plain Markdown. There is no
  program.
- One thin manifest per harness, all pointing at the same `skills/`:
  `.claude-plugin/`, `.codex-plugin/`, `.cursor-plugin/`, `.kimi-plugin/`,
  `gemini-extension.json`, `.opencode/`, `.pi/extensions/`, `.agents/plugins/`.
  The same guidance sits in `CLAUDE.md`, `AGENTS.md`, `GEMINI.md`.
- Startup is **one SessionStart hook** (~50 lines of bash) that injects
  `skills/using-superpowers/SKILL.md` as context, printing three JSON shapes
  depending on the platform.
- `hooks/run-hook.cmd` is a cmd/bash polyglot; no bash on Windows → exit 0 and
  the plugin still works.
- **No per-edit hook at all.** The Codex manifest declares `"hooks": {}`.
- Harness differences are isolated in the skill's `references/*-tools.md`.

It is portable because its payload is instructions, not a program. Our
non-portable part is only the hook wiring; the checker is a CLI any harness can
run.

### P7 — It fires at the wrong moment, on the wrong unit

The failure is found after the work is finished, at the level of a whole page,
by a human comparing pages. The plugin runs per file, per edit, during step 4.

### P8 — The correction typed by hand is exactly the slot the tool has

"Look at this page for reference; there we use this component; this button has
these settings" is a **reference screen + vocabulary + prop values**.
`src/sources/reference.ts` models it and `statedConventions` lets it gate.
Nothing ever asks for it, so it arrives by hand, after the mistake, every time.

### P9 — The knowledge base describes instead of instructing

Prose fragments, retrieved lexically, delivered after the file is written, with
nothing obliging anyone to act on them. A library nobody visits. What is missing
is not more corpus — it is a **procedure with slots to fill in**.

## What "pattern" means

Sharpened while talking through the reference-page case.

**A reference page is an example, not a specification.** Its shape holds both the
pattern and that page's own particulars, and copying it wholesale is what
produces a page that is *almost* right.

**The separating operation is intersection.** What repeats across several pages
of the same kind is the pattern; what appears on only one is that page's own
business. Intersection is mechanical and needs no vocabulary — `usage.ts`
already does it for props, reporting only values every sibling agrees on.

So the reference page's real job is **not to be copied** but to say *which
family to intersect*: take its kind, find the other pages of that kind, and
intersect them.

**Intersect per level**, because the invariant differs at each:

- skeleton — holder and the order of regions
- vocabulary — which component sits in each region
- configuration — which props each component always receives
- wiring — which handler shapes recur

**Reference minus invariant = that page's particulars** — the explicit list of
what must *not* be copied. Nobody computes it today, which is why it is supplied
by hand afterwards.

Limit: intersection needs at least three pages of a kind. For a genuinely new
kind there is no family, and the honest answer is "no pattern found — you
decide, and this page becomes the first of its kind". Same for a 30-page
refactor: the first page done right is the seed and no intersection is needed.

## The concept, cleaned up

**The job is not to grade code after it is written. It is to make the decision
*before* it is written — by supplying this project's own answer for each part of
a screen — and then to check a whole set of screens against the answer that was
agreed.**

Three parts, and none of them can do the work alone:

1. **An anatomy and a procedure** (instructions, portable text). The ordered
   roles a screen has, the fixed reading order, and when the agent must stop and
   look rather than write.
2. **An extractor** (a deterministic program, no vocabulary of its own). It
   answers *what does this project put in this role, in what order, with which
   props, and what is this page's route trail* — from the code itself.
3. **A contract for the task** (a small artefact, approved once by a person).
   The answers, written down. It is the input the writing is done from, and the
   thing the final comparison measures against.

**Three moments, none of them per keystroke:**

- **At the start of the task**, beside the requirements and the plan: pick the
  family of screens, extract, produce the contract, have a person approve it.
- **While writing each file**: the contract is *re-read*, not remembered. It is
  an input, not a critique — which is why compliance stops being a matter of
  obedience.
- **At the end of the batch**: every touched page is compared against the
  contract, and the deviations are listed page by page. This is what replaces
  the user opening the pages and comparing them by eye.

**What this deletes:** the built-in MUI vocabulary; the per-edit gate as the
main surface; the prose corpus as the load-bearing input; and the framing "is
this wrong?", which needs a vocabulary no tool can have.

**What it keeps:** layer detection and the inventory (as *facts* — what exists,
what is exported, what is deprecated); the style-literal check (CSS is
universal); the sibling-usage extractor; the repeated-shape comparator; the log;
and the marker rule that keeps derived material from gating until a person
accepts it.

**Portability follows for free:** the instructions travel like any skill, the
extractor is a CLI any harness can run, and only the wiring is per-harness.

## The shape: a hybrid, organised like superpowers

The plugin becomes **a library of skills and rules that the user's own agents
orchestrate**, plus a deterministic CLI those skills call for facts. Not a hook
that grades edits.

This follows how the work is already done: the requirements agent and the
development agent already compose superpowers skills, built-in skills
(code-review, simplify, security), and the team's own rules. Ours must drop into
that composition — each skill nameable, self-contained, and explicit about what
it produces, so an agent author can place it at the right point.

### The skills

| Skill | When | Produces |
| --- | --- | --- |
| `uic-pattern` | start of the task, beside the plan | the contract: skeleton, role → component, props always set, and the reference page's *particulars* (what not to copy) |
| `uic-screen` | writing or changing one screen | the screen, written from the contract and the role checklist |
| `uic-batch` | applying a decided pattern to N pages | a queue, one file per turn, contract re-read each time |
| `uic-verify` | end of the batch, before the PR | deviations from the contract, page by page |

`uic-pattern` asks for a reference page first (no inference at all); only failing
that does it extract from the family and present a draft for approval.

`uic-batch` seeds from the first page done right — no intersection needed when
the canon already exists — and never holds all the files in context at once.

### The CLI, as a supplier of facts

- `uic pattern` — the intersection across a family: skeleton, vocabulary per
  role, props always set, recurring wiring shapes, and reference-minus-invariant.
- `uic route <file>` — the route trail, so breadcrumbs stop being guessed.
- `uic diff --contract <c> <files…>` — per-file deviation from the contract.
- `uic inventory`, `uic scan` — what exists, what is exported, what is
  deprecated.
- `uic check` — only what is certain and vocabulary-free: raw CSS literals,
  deprecated usage.

### The hook, reduced

`SessionStart` injects one short rule: *when building or refactoring screens,
establish the contract first.* `PostToolUse` becomes optional and narrow, or
goes. The per-edit gate is no longer the product.

### Rules and portability

The anatomy (roles, reading order) and the "what not to copy from a reference"
rule ship as rule files the skills read and agents can import, with one file per
ecosystem convention (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`) as superpowers does.

### Roles are universal; names are local

Header, breadcrumb, navigation, content, footer, actions, grid with filters,
global search, detail, form with validation — these exist in every framework and
every design system. `Button`, `TextField`, `DataGrid` exist only inside one
library. So the built-in vocabulary must be **roles**, and the mapping *role →
this project's component* is learned from the code or asked once. This is what
kills P1 at the root.

### The reading order is a mechanism, not a style

"Top to bottom, then left to right." A fixed traversal makes two readings
comparable, and comparable readings can be diffed. Without it every reading
differs and nothing can be compared.

### The anatomy is a list of questions, not requirements

Per kind of screen: the ordered roles, each answered either "this project puts X
here" or "not applicable here". Otherwise we impose a sidebar on an application
that has none. Answered once per project, re-read for every screen — which is
also the cure for P0b, because it is re-read rather than remembered.

### Breadcrumbs are the proof case

Got wrong nearly every time, for a structural reason: a breadcrumb encodes the
**navigation hierarchy**, which is not visible in the file being edited. It is
in the router. The right element is an instruction *plus* a mechanical fact —
"derive the trail from this page's route hierarchy" — and the trail itself can
be computed from the router and handed over before the writing, not after.

### Division of labour

- **The machine supplies facts**: the region order here, which component sits in
  this role on the other pages, the route path, which props are always set.
- **The instruction supplies the procedure**: when to stop, what to enumerate,
  in what order, and what not to copy from the reference.

### The rule that keeps "curated, never inferred" intact

Derivation from surrounding code **is** inference — no way round that. What
survives is narrower: *derived material proposes; a person accepts it once, for
this task; the accepted contract is what may gate.* The project already has this
mechanism — generated knowledge carries a marker and cannot gate until a person
removes it (#99). Preferred order: the user names the reference page (no
inference at all); only failing that, extraction shown as a draft for approval,
never used silently.

## Derive or store: the line between them

The prose knowledge base is not replaced by a better corpus. It is split in two.

**Facts about the code are derived every time and never stored** — the skeleton,
which component sits in a role, which props always accompany it, the route
trail. Derivation costs milliseconds; a stored copy can only be wrong. Every
staleness problem this repository has had (`uic audit`, the generated marker,
all of #99) exists because of the copy.

**Decisions a person made are stored, because they cannot be derived** — "the
canonical detail screen is this file", "we are migrating from X to Y, prefer Y",
"the breadcrumb comes from the route, not the title", "an empty state is
required". Extraction can say what repeats; it cannot say which of two competing
patterns is the one the team is moving *towards*. The older one is more common,
so derivation picks it.

The repository already discovered this once: `prefer` in `.uicrc.json` is the
single thing it concluded must be told rather than derived. Intent is that
class, and it is the only one.

So:

- **A decisions file per kind of screen** — 5-20 lines, mostly pointers.
  Committed, reviewed in a PR, shared through git like code. Checkable
  mechanically: does the file it names still exist?
- **The contract is ephemeral.** Assembled at the start of a task from the
  pointer, the decisions and fresh derivation; re-read per file; discarded with
  the task. Never committed, so it can never go stale, and review lands on the
  decision rather than on the derived material.

Claude does not start from nothing — it starts from a few lines of intent, and
fills the rest from the code as it is today.

## Cost, as a budget rather than an intention

The saving is one sentence: **the program reads, the model reads the
conclusion.** `uic pattern` reads eight pages and returns twenty lines; reading
those pages directly is what is expensive today.

Per task, not per file:

| what | when | size |
| --- | --- | --- |
| anatomy (roles + reading order) | once, when a skill runs | 25-40 lines |
| decisions for this kind | once | 5-20 lines |
| contract | once, then re-read | 10-30 lines |
| deviations | once, at the end | only the pages that deviate, one line each |

Per file in a batch: the contract only. Thirty files stay under ~15k tokens —
less than a single round of manual correction costs today.

Six commitments that hold it there:

1. The CLI returns conclusions, never evidence.
2. Nothing loads unless a skill is invoked. No per-edit injection.
3. One contract is loaded, never the store.
4. Hard caps, written as numbers: contract ≤ 40 lines, deviation report ≤ 20
   entries plus "…and N more".
5. `SessionStart` injects one sentence, not a skill. Superpowers may inject its
   whole entry skill because it *is* the operating manual; a domain tool may not.
6. No model call inside the plugin. The thinking happens in the session that is
   already running.

The honest risk is not that it costs tokens. It is that it costs tokens **and
does not remove the correction rounds**.

## Universality — of process, not only of repository

The plugin must assume no workflow. One team runs a requirements agent, then a
development agent that composes superpowers' TDD loop, then built-in code review
before the PR; the next team does none of that. The three insertion points that
fit the first are an **example**, not the design.

1. Every skill is invocable on its own, and none requires another to have run.
2. Missing input degrades rather than refuses: without a contract, `uic-screen`
   derives on the spot — more expensive, weaker, still working.
3. **The artefact is the interface, not the process.** A contract at a known
   path, like a target in a Makefile: any agent, any harness, or a person can
   produce and consume it.
4. CLI first, skills second. The verbs assume nothing — a team with no agents at
   all can run `uic pattern` and `uic diff` in CI or a pre-commit hook.
5. Skills trigger on the situation in the code — "a new screen is being built",
   "a pattern is being applied across many pages", "a PR with UI changes is
   being prepared" — never on a position in somebody's pipeline.
6. No required configuration and no required order.

Where it does insert into an agent flow, it must not take the flow over:
superpowers owns the process, this owns the domain facts. In particular the TDD
rhythm is not touched — a contract violation is a red, checked in the same loop,
and structural assertions go into the test suite only if a team asks for them.

The cost of this, stated rather than hidden: **the plugin cannot enforce
sequencing.** Its strength is proportional to how much intent has been said
once.

Two universalities, often confused:

- **process** — assume no workflow (the six points above);
- **framework** — assume no component names (roles, not names; P1).

## What the first run of `uic pattern` found

Built under #114 and run against two real repositories.

**The three readable levels are right and useful.** On an Ionic app:
`IonPage > header, content`; header → `IonHeader`, content → `IonContent`; and
the configuration every screen shares — `IonContent color="light"`,
`IonList inset`, `IonButton expand="block"`, `IonInput fill="outline" mode="md"`.
That last level is exactly what P0c is about.

**Family selection by kind is inert on real projects.** A list screen is still
intersected with the forms beside it, because `archetypeOf` is a *name list*
(`Table|DataGrid|DataTable|TextField|Select…`) and matches nothing in either
repository. `kind` came back null on both. The mechanism is built and tested;
it cannot fire until #123.

**Worse, and more important: role recognition is itself a name list.** On a
Next.js app whose screens are `DashboardShell` holding `DashboardHeader`,
`regionsOf` recognised **no roles at all**, so the skeleton had a holder and an
empty region list, and vocabulary and configuration came back empty with it.

Roles are universal. Recognising which component *plays* a role from its name is
not, and no amount of adding words to the list makes it so. This is the real
bottleneck, and it makes #123 bigger than deleting MUI's vocabulary: role
detection needs a mechanism that is not a word list — position in the layout,
what the component itself renders, or a line in the decisions file where a person
says "our header is `DashboardHeader`".

## What was built, and what the measurements say now

Everything above was worked through as #114–#124 plus #131–#133. Measured across
nine repositories on seven stacks, with the shipped bundle:

| what | before | after |
| --- | --- | --- |
| a kind of screen | `null` everywhere — the archetype was a word list | the holder the family shares: `IonPage`, `div`, `AppShell` |
| the chrome | not read at all; the page holds only the body | the layout file, and what it provides |
| where a screen belongs | nothing | route and trail on all seven stacks, in both routing styles |
| raw elements | `Button`, `TextField`, `MenuItem` — one library's names | the elements the family avoids, named from the HTML specification |
| a project with no layout components | an empty answer that read as "all fine" | `built: markup`, said in words |
| per edit | ~1 KB of ignored observation | findings, and deviation from an approved contract |

Three defects the suite could not have found, all from running against real
repositories:

- The family search **left the project** and read a neighbouring repository's
  screens. It reported that project's own layout components as things not to
  copy (#133).
- `uic pattern <file>` printed its own usage, because a missing flag made the
  first argument look like the flag's value.
- `uic place` read a route out of a mock, then out of a parent's `redirect`, on
  the same repository.

**What remains unproven.** The whole loop has never run in the monorepo it was
built for — every measurement here comes from repositories with no core layer
wrapping a design system. And nothing has yet been measured on the thing that
matters most: whether a task carried through `pattern` → `screen` → `verify`
produces fewer corrections than the same task without it.
