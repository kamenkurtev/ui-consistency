Try ui-consistency

A plugin that checks the screens your agent writes against the screens your project already has — in the same turn as the edit, not in a pipeline two days later.

v0.14.79 Node 20+ No build step github.com/kamenkurtev/ui-consistency

What it actually does

It works everything out from your repository. There is no built-in list of good components, no framework it prefers, and no model call anywhere in the tool — so it costs nothing per edit and works with whatever agent you already use.

A finding looks like this. @acme/ui is a placeholder for whatever your packages are called; the tool has never heard of it, it read your dependency graph:

apps/orders/src/OrderList.tsx:1
Button is imported from @vendor/ui.
@acme/ui exports Button and is nearer on this file's chain.
→ import { Button } from '@acme/ui'

Install it

  1. 01

    Add the marketplace and install

    In Claude Code, three commands:

    /plugin marketplace add kamenkurtev/ui-consistency
/plugin install ui-consistency@kkurtev-plugins
/reload-plugins

    Nothing to build and no npm install — the bundle ships committed. Node 20 or later is the only requirement.

  2. 02

    Open a project and edit a screen

    That is the whole setup. The per-edit check registers itself as a PostToolUse hook and reports in the same turn, while the agent still has the file in its hands and changing it costs nothing.

    You do not have to run anything for it to know what your screens look like. On the edit your agent is already making, it derives what screens of that kind look like here and hands back only what this one does differently — nothing saved, nothing approved, nothing failed.

  3. 03

    Ask it whether it is doing anything

    This is the step worth not skipping, and the honest part. On day one, on a project that has written nothing down, what runs is the deterministic half — raw colours and lengths, an emoji standing in for an icon, imports resolving to the wrong layer — plus the derived advisories. The curated checks stay quiet because nobody has curated anything yet.

    > use ui-consistency:reach

    It answers level by level, and there are only three answers:

    Works
    and here is what it read
    Quiet
    because your project has stated nothing — this is the design, not a fault
    Blind
    it cannot see here, and here is why

    No score and no grade. A level is never called working just because it produced no findings — that distinction is the whole point of the command.

What Tier 1 checks on every edit

Seven deterministic checks, roughly 0.12 s, no model. It is silent unless it is certain — a check that guesses gets switched off within a week, and a switched-off check costs more than every finding it would have made.

Real output, from a throwaway project:

src/Card.tsx:1
color: '#ff0000' is a colour literal.

src/Card.tsx:1
🔔 is an emoji used as an icon. Use the design system's icon component so it matches the others.

Numbers on spacing keys in sx are left alone — sx={{ mt: 2 }} is a theme multiplier, which is the correct form. Fixed widths and heights are left alone too: almost no design system has a width token. Tests, stories and __mocks__ are not checked at all.

There is deliberately no "that is a raw <button>, use Button" check. Saying that needs a built-in map from an element to a component name, which is a vocabulary — and on every project that names things differently it matched nothing and said nothing. Raw elements are checked against a contract derived from your own screens instead.

The skills, when you want to drive it

Invoke by name. None requires another to have run — where an input is missing they derive it or say so, rather than refusing, so you can start anywhere.

ui-consistency:patternwhat screens of this kind look like here
ui-consistency:screenwrite one against that
ui-consistency:rolloutapply it across many, one file per turn
ui-consistency:verifycompare the finished set, before a PR
ui-consistency:reviewa second opinion on one screen
ui-consistency:decidethe first screen of a kind, when there is nothing to derive
ui-consistency:reachwhich of the three silences you are looking at

There is also a CLI for a whole-project pass or a CI gate. It is not on your PATH — call the bundle directly:

node path/to/bin/uic.mjs check $(git ls-files '*.tsx')

It exits 1 if anything is wrong. check takes files, not glob patterns, and relies on the shell to expand them — a quoted glob is refused rather than silently checking nothing.

One thing to be careful about when you report back

If you test this on our own codebase, keep the numbers and drop the names. When you file something, rename every component, screen, route file and test-id prefix to a neutral equivalent of the same shape — OrdersGrid for a PascalCase grid, app-orders-grid for its selector form, acme-orders-page for a test-id.

The repository is public now. The lesson and the counts are what make a report useful; the provenance is what you do not want in it.

Reporting something

The house style is a reproduction in an empty directory using the shipped bundle. It is worth the five minutes: it separates a defect in the tool from something about our repository, and it is what a fix gets tested against.

# copy bin/uic.mjs alone into an empty directory
mkdir -p /tmp/repro/src && cd /tmp/repro
echo '{"name":"r"}' > package.json
# ...the smallest files that show it...
node /path/to/uic.mjs check src/Thing.tsx
  • Say what you observed and what you expected, and paste the output unedited.
  • If the answer was silence, say which command was silent — that is the most valuable report there is, and the three silences above are why.
  • Issues go to the tracker.

Only the Claude Code path has been run end to end. Cursor registers sessionStart only and Codex's hook file is empty, so everywhere except Claude Code what you get today is the skills and the CLI, not the per-edit gate.
