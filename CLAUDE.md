## What this is

A plugin — Claude Code first, with manifests for Codex, Cursor and Gemini CLI — that keeps AI-generated UI consistent with the project's **own** component vocabulary and prop conventions, **while the code is being written** — not in a pipeline afterwards.

Claude Code is the only harness with the `PostToolUse` gate wired (`hooks/hooks.json`). Elsewhere the skills and the CLI are the whole surface. Do not write anything that assumes the hook is running.

Read these two before proposing anything:

1. `docs/concept.md` — what this is and why, in one document.
2. `rules/pattern-file.md` — what the tool writes down, and in what form.

That is the whole reading list, deliberately. It was six documents in a supersession chain, which is a list nobody finishes before a first change — and the rest of this file carries what those documents decided.

~~Everything else under `docs/` is a dated record and none of it is a reading list.~~ **There is nothing else under `docs/` (#48).** The specs, the findings and `design.md` are deleted: a record that has to be excluded from the name scrub, kept because it is quoted, and read by somebody looking for what is true now is a liability rather than an archive. Git history keeps every one of them, and the private archive repository keeps the history before the cut. What was still the position moved out first — the two load-bearing decisions into `docs/concept.md`, which already stated both, and the pattern-file format into `rules/pattern-file.md`, because it is an instruction and not a description of what the program computes.

The two load-bearing decisions, so they are not accidentally violated:

1. **The gate is deterministic, never LLM-based.** Everything that can fail a check is a plain program over the AST. A model on every edit would be slow and expensive and would get switched off. A model may *fix* what the checker reports, and — since v2 — may offer an opinion where no deterministic answer exists, but that opinion is advisory, off the edit path, and can never block anything.
   **Deterministic does not mean the program decides.** A check may report what is
   true *of the file* and never what ought to be true *of the project*. `#ff0000` is
   a hex literal, `12px` is an absolute length, `Button` came from a layer further
   than the chain allows — facts. That a token belonged there is a judgement about
   a design system, and the program does not get to make it.

   That line has been crossed, and the crossings are where this keeps breaking:
   `takesLength` is a hand-written list of which CSS properties a design system
   covers, and `SPACING_KEYS` and `SCALED_IN_SX` encode MUI's theme semantics. Each
   is a small model written by hand, and each fails the way small hand-written
   models fail — silently, on the neighbouring case. `takesLength` dropped fifteen
   keys once, and nothing noticed.

   **So: stated by the project, or evidence.** A literal the project has said
   something about — a theme, a token file, a written rule — is a finding. A
   literal it has said nothing about goes into what the agent is handed, beside the
   sibling screens and the rules, and *the agent* decides. The plugin exists to be
   developed with an AI; its job is to put the right facts in front of that AI, not
   to reimplement its judgement in TypeScript.

   The counterweight, which is measured and not theoretical: reporting every
   literal floods. Widths and heights alone were 168 of 372 findings on Backstage,
   nearly all legitimate, and a check that floods is switched off — after which it
   costs more than every finding it would have made. So the answer is not "report
   everything"; it is "report what was stated, hand over the rest".

2. **Conventions are curated, never inferred from surrounding code.** Inferring from neighbouring files averages in code nobody has touched for a year and turns existing mistakes into enforced rules. The developer nominates canonical exemplars.

   **A named reference and a derived family are two modes, and they carry
   different weight.** "Use `OrderList.tsx` as reference" is a choice somebody
   made: frequency never enters, so the risk this decision exists to prevent —
   enforcing the most-copied mistake — is not present at all. A family read with
   nothing named is statistics, and from an AST thirty pages sharing a convention
   and thirty repeating one old mistake are indistinguishable.

   The code already works this way and no document said so. `pattern.ts`: *the
   reference is an example, not a specification: its shape holds the pattern —
   otherwise a page votes on whether what it does is what everyone does.* The
   reference gives the shape; the family only separates what repeats from what is
   that page's own business. `canon:` in the decisions file is the standing form
   of the same choice.

   So a user who always names a reference is not exposed to the second mode, and
   has no way to know that. Say it where they will read it.

## Architecture

One deterministic core, several thin surfaces:

- `core` — changed files + knowledge → list of findings (`src/core/engine.ts`)
- prompt adapter — `UserPromptSubmit`, **before anything is written** (#27, `src/cli/prompt.ts`). Where the prompt is about screens it puts the patterns the project has written down in front of the agent, and says plainly when there are none — **and where none covers the kind, the instruction is to establish one, not to ask for one (#38)**. A channel that only reports what a project has written down opens onto nothing on a fresh install, which is the whole case it exists for; the agent is already reading the code the pattern would be derived from, so it derives it and writes it down, and the user is asked nothing and runs nothing. An agent told the pattern first writes the right screen once; one told afterwards has to be persuaded to change working code, and each report it declines teaches that the channel is skippable. **`PreToolUse` is deliberately unwired**: its output accepts a permission decision and nothing else, so the only way to be heard there is to interrupt the write — which is the same failure with an extra step, and forbidden by *nothing derived may fail an edit*. The trigger is a list of English words, never of component names, and a prompt that is not about screens reads no file.
- hook adapter — `PostToolUse` on `Write|Edit`, returns findings to the agent in the same turn. **It speaks about the edit; the log keeps the file**: a finding outside the lines the tool call wrote is recorded and not injected, because telling an agent to fix a year-old line inside an unrelated change asks for churn it is right to refuse — and each refusal teaches that the imperative is skippable. `Write` is the whole file; an `Edit` whose text cannot be located says everything, since narrowing is only allowed where it is certain.
- CLI adapter — same core, whole project, for a pipeline
- **MCP adapter — `uic mcp`, and the only surface every harness has** (#33, `src/mcp/`). Claude Code is the one harness with the gate wired, so under Codex, Cursor and Gemini CLI the skills and the CLI were the whole surface and #27 — the pattern reaching the agent *before* the write — had no mechanism at all. All four manifests declare the server, so it starts with the plugin and nobody configures anything, and the agent can reach it on its own initiative. Six tools onto functions the core already computes, plus the pattern files as **resources** — the half a CLI cannot offer, since the agent then needs no path convention. Three things it buys that are not the protocol: a typed array instead of a shell glob, which removes the commonest wrong call this tool gets; the root stated rather than assumed; and nothing new. **The protocol is written out by hand and not taken from the SDK** — a fourth runtime dependency and a second bundle against a promise kept everywhere else (Node 20, no install, one file), for six methods over newline-delimited JSON. Two rules of stdio that fail silently and are therefore load-bearing: **nothing may reach stdout that is not a message**, which is why the three core functions the tools call were moved out of `src/cli/index.ts` — everything in that file prints — and a message may contain **no newline**. Nothing requires it: the hook, the CLI and the skills work unchanged with no server running, and a wedged one degrades to silence rather than to a wrong answer.
- **`rules/` — plain Markdown, and the portable half.** Seven files since #48, `pattern-file.md` being the newest: the pattern format was a dated spec and is an instruction, so it lives here where a wrong rule is wrong visibly. Load-bearing and absent from this list for a long time: the knowledge that keeps breaking when it is written as a list in TypeScript belongs here instead, where a wrong rule is wrong *visibly* in a file somebody can read rather than returning an empty array. It needs no derived facts and works on every harness — including the three with no hook, which reach it through `AGENTS.md`.
- **The batch loop starts because the work is that shape** (#28, `skills/rollout`). Where a prompt names a set rather than a screen — *all the*, *every*, *the rest* — the prompt adapter names the rollout loop, from a list about English exactly like the one that decides whether a prompt is about screens at all. **Named and not begun**, deliberately: a hook that wrote a queue to disk off a regular expression, before a file had been read, would start a process nobody asked for on a guess. The judgement that the set is real belongs where the files are open.
- skills (`ui-consistency-*`) and `/uic-fix` — loaded only when invoked, and **the session hook now says when each of the seven fires and in what order** (#9). The line it used to emit named one of them and ended *"nothing is generated and nothing is spent until somebody asks"*, which was written to promise a cost and reads to an agent as *do not act unless asked*. The promise is kept and said as what it is: nothing is spent until UI work starts. The same text is in `AGENTS.md`, because three of the four harnesses have no hook and that file is how they reach it.

Keep the core independent of the hook. Everything else is a wrapper, never a second implementation.

**The program is the fact supplier; the rules and the skills are the instructions.** The ratio was 19:1 in favour of the program, which is the inverse of the shape that makes a library of instructions portable at all. Where a rule and a list in `src/` would carry the same knowledge, only one of them may exist — two copies is the one outcome worse than either alone.

## Scope

**v1, shipped: import resolution.** A symbol imported from a layer less derived than the file's own chain allows. The layer chain is derived from the dependency graph, never declared.

**v2, shipped: design-system consistency at seven levels** — page pattern, layout, component reuse, style, props, deprecated markers, and imports last as a supporting signal. Imports are the symptom, not the subject.

The first two of those assume a screen has *named regions filled by sibling components*, and the commonest real page shape has none: a holder plus one child, with the header and the title in the holder's props. `vocabulary` and `regions` are then structurally empty — measured so on a real React monorepo and a real Angular one — and two blanks read as *no convention here*. The contract says which shape it found (`regionsIn`) and what the holder holds (`body`), so an empty answer is never mistaken for a clean one.

Those are the *levels the design addresses*, and they are not the same seven as the deterministic checks listed below. Component reuse in particular is no longer a check at all: it is delivered through the contract's `avoids`, which a person approves. Reading one list as the other is what produced three documents describing a raw-element check that does not exist — it was removed on 16 August and they were corrected on 18 and 19 August.

Seven deterministic checks run on every edit (`src/core/engine.ts`): imports, hardcoded style literals, emoji-as-icon, deprecated usage, prop values against an injected set, curated page rules, and curated `use X, never Y` substitution rules. Above them the fuzzy levels, and skills on demand.

**There is no raw-element check on the edit path**, and its absence is deliberate. Saying "`<button>` should be `Button`" needs a built-in map from element to component name — a vocabulary — which is what an earlier version removed, because it matched nothing and said nothing on every project that names things differently. Raw elements are checked against the contract's `avoids` (`src/checks/contract.ts`), where the answer comes from the project's own screens and a person has approved it — and that check was dead on every template dialect until it was fixed, reporting *success* on a screen rendering the forbidden element.

**No model is called from anywhere in this tool** (`src/ai/advice.ts`). The fuzzy half assembles the evidence — the project's rules, what this file is, what the neighbours agree about — and hands it to the agent already in the room, because a hook cannot require credentials a free plugin has no business asking for. That is also what makes the tool model-agnostic: there is nothing to configure, so whatever model the harness runs does the fuzzy half.

**Decide before writing; grade nothing afterwards.** `uic pattern` derives what screens of a kind look like here — holder and role order, the component in each role, the props ~~they are always written with~~ **most of them are written with, and how many** (unanimity meant the more drift a family had the less was said about it — `dataTestId` at 7 of 8 was dropped; every sentence now states the strength), what the layout provides, what belongs to the reference alone, and the raw elements the family avoids. **A "kind" is assembled from the pattern file first, the route table next** — a pattern file naming this screen is a person saying *these are one kind*, reviewed in a pull request, and nothing read off the code outranks that (#5, `from: 'pattern'`); the route table is the only place a project otherwise *states* which screens are registered beside one another — and from the folders around the screen only when neither does. That sentence now carries the weight of the whole level, so **the route reader's accuracy is what it rests on**: the unit is the route *object*, not the line, and the path composes down the tree. Reading it as text gave 52 invented paths out of 117 screens on one real repository, each borrowed from a neighbouring entry. A path and a registration are two facts: a pathless entry states no path and still names the table, and losing the second is how a screen falls back onto its own folder. **The path may not be in that table at all** — a routes array exported from one file and mounted under a path in another, which was 50 of those 117 screens — so ~~where the entry states none~~ **for every entry in it (#1)**, the table that mounts *this table's exported array* is looked for and its path composed on top. It is found by content and never by file name: the mounting file is called `shellConfig.tsx` on that repository and matches no routing-file pattern. Two tables mounting the same array, an unfinished search, or a table whose exported name is too generic to be evidence all answer `path: null` — a partial prefix is never presented as a whole path — and where the entry states a path of its own they leave it exactly as the table wrote it, because refusing to compose is not refusing to answer. The original was right about the mechanism and wrong about its reach: a mount shifts the entries that state a path just as much, and `{ path: 'detail/:id' }` under a table mounted at `orders` answered `/detail/:id` — a partial path presented as a whole one, which the same paragraph forbids two sentences later. Two corrections came with it, both wrong answers older than the issue and neither needing a mount to reach: a parent's trailing `*` is how it admits children and not a segment of their paths, and a path the table wrote **absolute** is already whole, so nothing above it composes on. A parent and the array it mounts written in one file compose now as well. **And the path may not be a literal at all** (#36, `src/sources/constants.ts`): a project that keeps its paths in an enum, a frozen object or a module of exported strings writes every `path:` as a name, and reading only the literal answered `path: null` for every screen in one real application — the registration found 117 times and the path never. Constants the table can see are resolved **by value**, from its own declarations and one hop through the imports that bring in a name a path is actually written with; nothing reads `RoutePaths.Dashboard` as `'dashboard'` from the member's spelling, and a template literal with one part it cannot resolve answers null rather than a partial path. It costs nothing where there is nothing to resolve — the names are collected from the table's own `path:` positions first, so a table of literals reads no module, which matters because a route table imports every screen it registers and this runs on the registration. `pathFromConstant` says which it was. The measurement #1 asked for first does not exist publicly — seventeen repositories, one mount, refused twice over by design. The family is untouched by any of it, because the family comes from the registration. **A third channel since #35** (`holderSiblings`, `src/sources/siblings.ts`): where neither the route table nor the folder produces a family of the reference's own kind, the application is searched for screens sitting in the **same holder** — which is the rule `ScreenPattern.kind` always stated and nothing ever asked. The folder walk collects by proximity, and in a project giving every screen its own folder proximity is alphabetical accident: on a reproduction it returned 12 candidates of which all 12 sat in a different holder, so a family of 8 answered *"fewer than three screens of this kind"*. It answers `from: 'holder'` — weaker than a registration somebody wrote, stronger than a guess about folders. **`uic pattern` asks for it and the edit path does not**: 376 ms end to end on an 808-screen application against the 37 ms cold budget, the same measurement that keeps `uic tree` off that path. Bounded to the nearest `package.json` rather than the workspace, because one app's screens in another app's family is a wrong answer and not a slow one — and silent where no package bounds it. In that fallback a screen's own folder is not its family: a page and its grid, its dialog and its hooks are one screen. **That was the rule and for a while it had no mechanism** — the shipped fallback did not enforce it, so a page's own panels became the family it was measured against and the derived holder contradicted the page itself. Once a derived contract began reaching the agent automatically the stakes rose, and three guards enforce it: nothing the screen imports may be its family, a folder-derived contract whose holder the reference does not sit in is discarded, and the sentence handed over names where the family came from. Each turns a wrong derivation into a miss. **Two more since #5, and both are misses by design**: a folder holding a mixture is refused outright rather than described (a dialog was measured against an amount cell, a currency field, an attachments panel and a history tab), and a hook never enters a family however much JSX it returns — `use` followed by a capital is the naming React itself enforces, in the same class as `.test.` and unlike any list of component names. A dialog with three real siblings of its own kind now answers, which is most of the screens on a real project: 202 dialogs against 132 pages. `uic diff --contract` measures the finished set against it — **against a pattern file as well as a saved JSON contract, and it says which it read** (#11): it faults a level the pattern says every screen has, an order a screen inverts, and a prop the family writes with the strength the pattern states, and it hands over what it cannot evaluate — the prose rules, and any slot written for a person — because printing nothing for those would let a screen pass against rules nobody checked. It applies the pattern **per file** and names the paths of another kind rather than measuring them, which is the #3 defect as it stood on this path. **Nothing derived may fail an edit** — and nothing does: the hook puts contract deviations into the agent's context, never into a failure.

**What a screen is made of is one level below the file that names it** (#10, `src/sources/tree.ts`). The screen file is a wiring file: it renders one or two components, and the anatomy that makes it *that kind of screen* is inside them. Classifying 132 real screens by what the file itself renders put 11 in the largest bucket; following one hop through the repository put 26 there. **What it reads was wrong on three of four real screens, and #31 is where that was fixed**: the root is what a component *returns* rather than the largest JSX in the file — a detail pattern declaring its tabs as objects had a bigger `content:` than its own four-line return, so the answer was the loader and the screen was invisible; a child inside `{cond && <X/>}`, a ternary, a `.map` or a fragment is walked, which is how most screens gate on data; nothing is reported as its own child, and the fact that used to say — the holder resolved into a workspace package — moved onto the node it is about; and content a screen passes as **data** is followed and said to have come from a prop, because `<SectionTabs tabs={tabs} />` was a leaf while the whole anatomy sat in `tabs[].content`. A content prop that cannot be read in the file is named as unresolved, and only where the element holds nothing from anywhere else — a prop nobody can read beside a child that is right there says nothing, and a check that floods gets switched off. The walk counts depth in **file hops**, states the bound it applied, and says why each branch ended — `external` is where it is meant to stop, `unresolved` is a specifier it could not follow, and merging those two is a walk claiming a depth it did not reach. **A package of the same workspace is neither** (#17): on the monorepo shape this plugin is built for the project's own design system is imported by package name, and calling that `external` said *nothing below here is our business* about the project's own code — 53 of 62 children on a real repository. It resolves, it is named, and it is deliberately not descended into: `Page / Header / Content` is the vocabulary a pattern wants and that layout's internals are not. **And a file whose whole output is one component is a wiring file**, so its root is followed — that is the hop the level exists for, and following children alone never took it. `uic tree` is the surface, and `uic props` and `uic group` are the other two facts the same scans were written by hand for (#7): which props each of a set of files writes on one component, and a set of screens grouped by what they are composed of — where a name survives into a group's signature only if more than one screen renders it, so nine list screens that differ on the name of their grid are one group and not nine — and a signature made **entirely** of placeholders is not a group at all but a list of screens sharing nothing, which on a real repository was seven unrelated files presented as the second-largest pattern (#17). **A signature that carries no shape is not a group, and at full scale that was the largest "pattern" in a project** (#58). On a real 1 955-file React monorepo `div` was reported first, at 27 screens, above a modal with a header, content and footer at 7 of 8 and a page holder with an optional footer at 2 of 7 — which are what the command exists to find. A tree of one node states no holder-and-child relationship, no order and no role: it is the same non-answer as a signature made entirely of placeholders, arriving by a different route, and the optional fold makes it worse because one node is a subsequence of very nearly everything, so it attracts members instead of being absorbed. **Unless that node is a slot** — `*Grid` over two screens is a role the project's own naming stated, which is the whole of #6's mechanism, and a literal name shared by 27 files is not that. Named in its own bucket rather than dropped, because a leaf is not a failure.

**And a grouping has to be distinguishable from a list, in the heading.** 527 groups over 833 screens is not 527 findings; it is a grouping that found nothing, and printed as a ranked list it reads as the opposite. So the screens-per-group ratio is stated and, below 2.5, said in words. The proportion of the files given that were counted as screens is there for the same reason: two real React monorepos of comparable size disagreed by a factor of three, 224 of 1 606 against 833 of 1 955, and a number nobody can see is a disagreement nobody can find. ~~That disagreement is **not** yet explained~~ — **one cause is found and fixed** (#62): the import chain broke at the first specifier not written relatively. `importedBy` resolves `./Grid` and returns `null` for a package name or a `tsconfig` alias, which is right for the family search — a screen's own parts sit beside it — and wrong for the grouping, because on the monorepo shape this plugin is built for a screen renders components imported exactly that way. So the chain ended there and every component below it survived as a screen of its own; `uic group` now asks the same alias-aware resolver `uic tree` uses, and the family search keeps its relative-only reach. **Whether that accounts for the whole factor of three is unmeasured**: it does not move on the public monorepo used as a stand-in, where cross-package imports go through index barrels rather than to the files in the given set, so it is proven on a fixture of that shape and open until it is measured where the disagreement was found.

**Two more since #32, and both were fragmentation rather than a project's conventions** — 11 files answered 9 groups, and 14 answered 10. A file that is not a screen is no longer counted as one: what a name enforces is excluded (`.test.`, `.stories.`, a `use`-prefixed hook, a `.helpers.` segment — words about a file's role, never about a project's components), and so is **a file another file in the set imports**, which is structural and is the same rule the family search obeys. And a group differing only by an element some members render is one pattern: signatures fold where one is a subsequence of another, taking the *smallest* difference and refusing a host with more extra lines than the candidate has of its own — the longest host matching first folded a screen into an unrelated group that merely rendered more, which is worse than the over-splitting the fold exists to fix. The optional line then carries `N of M`, so a folded group claims no more agreement than it has. **It is not on the edit path**: eight children at every level costs 20 ms at depth 3 and 115 ms at depth 4 against a 37 ms cold budget, and whether the derived contract should read through children is a question for the artifact #4 defines, not one to answer by wiring it in unmeasured.

**And nobody has to run anything for it to know**. Where an approved contract **covers the kind** it wins; where none does, the pattern is derived on the edit already being made and said to be derived. *Covers* is load-bearing and until #3 was not enforced: a single saved contract was applied to every screen file whatever holder it sat in, so the first `uic pattern --save` — step 2 of the skill — turned every dialog, panel and tile in the repository into a page that had left its contract, in the approved imperative. A contract now describes its own kind only, one of them or ten. `uic pattern` stays as the explicit form for when somebody wants to look, not as the way the knowledge comes into being — requiring it per kind is why a project that had written nothing down got 93% an import checker. Derived answers are cached in `src/sources/pattern-cache.ts`, keyed by the kind, the area and the mtimes of the files they came from, with the same accepted staleness as the package graph: a miss, never an invented finding. 37 ms cold, 0.5 ms warm, and at most once a minute per file behind the debounce. What a derived contract buys is that file thirty is measured against the same thing as file one, which is the whole of the drift problem and needs nobody's signature.

Approval belongs at the one place derived material can fail something: a person putting `uic diff --contract` in a build gate. Asking for it before the work is a gate on a path that gates nothing, and it was on the batch path until it was taken off.

**The only thing stored is intent**: `.ui-consistency/decisions/<kind>.md`, five to twenty lines, mostly pointers — and, since #4, `.ui-consistency/patterns/<name>.md`, one Markdown file per pattern rather than one JSON per screen (`rules/pattern-file.md`, `src/knowledge/pattern-file.ts`). Prose, because the three things a pattern must state cannot be data: an alternative a slot allows, a rule no checker can evaluate, and the reason one screen is allowed to differ. **One section has a grammar** — `## Props`, a `###` per component and a bullet per prop with its strength — because *"writes the table without `density`, which 5 of the 6 screens of this kind write"* cannot be produced from prose nobody agreed the shape of. A strength written as a count is parsed; one written as a sentence is kept as one, because inventing a number is worse than carrying a sentence. The saved JSON contract stays ephemeral and keeps working; ~~a pattern file is committed, because a thing a person approved in a pull request has to still be there tomorrow.~~ **A pattern file is committed, and since #38 the tool writes the first draft of one itself** (`uic pattern <screen> --establish`, `src/knowledge/pattern-write.ts`) — so *committed* no longer implies *approved*, and the two are now told apart by a field rather than by prose: `derived: true` in the frontmatter, with the date. The reason for the change is that the sentence described a file that on a fresh install did not exist for any kind, so the channel #27 opened before the write reported that nothing had been written down and then asked somebody to run a command — which is how an installation stays silent through a full day of real UI work. What is written is the measured half only; the three things that cannot be data are named as missing under `## Still to be written`, because inventing a rule nobody stated into a file somebody is about to approve is worse than an empty section. Approval is still the one thing the tool never does: a person putting `uic diff --contract` in a build gate remains the only place derived material may fail anything. The staleness that ephemerality was avoiding is answered the way everything else here answers it — the intent is stored, the facts are derived, and `uic patterns` reports what has moved at the point the pattern is used. **Reporting it was where that stopped, and it stopped one step short** (#28): the only ways forward were a hand-edit or deleting the file and re-establishing it, which throws away every sentence somebody wrote — so the report named no way to act on itself, and *"re-derive before trusting it"* could only be followed by ignoring the pattern. `uic pattern <screen> --refresh` rewrites what was **counted** and leaves every other section exactly as found, `## Still to be written` above all, because the tool wrote that one *and* invited a person to answer it and `derived: true` cannot say whether they did; a file carrying no `derived: true` is refused outright, having no derived half. The trap in it is worth keeping written down, because the whole suite was green with it in: **a refresh may not read the file it is refreshing.** The pattern-file channel outranks everything read off the code, so re-deriving with the file in place read its own member list back as the family — measured on the shipped bundle as `read: 4 files` and an unchanged member list after a fifth screen of the kind was added, with `from` flipping from `holder` to `pattern` as the only tell. **Where that intent comes from was, for a while, nowhere** — a setup command was deleted and nothing replaced the asking, so the commonest answer in the tool (*"fewer than three screens of this kind"*) ended the interaction. `skills/decide` is the surface that asks: it walks `rules/anatomy.md` as questions, records *"not applicable"* and *"undecided"* as real answers, and writes only what was said. Facts about the code are derived every time, because a stored copy of what the code says can only be wrong — every staleness problem here came from such a copy. A dead pointer is reported where the decision is used, never by an audit somebody must remember to run.

**No component name may be hardcoded anywhere a finding can come from.** A test enforces it. Roles are universal; names are local, and a built-in vocabulary made the checks silent on every project that names things differently — silence being indistinguishable from a clean result.

**A family fills a role under a different name in every screen, and counting by name never sees it** (#6). `OrdersGrid`, `InvoicesGrid`, `CustomersGrid` — none of them reaches a majority, so `configuration` described the holder alone: measured on a real family of four it had exactly one entry, while props are precisely where a family drifts. The shared trailing word is the project's own statement that they are one role, and a slot entry (`*Grid`) carries what those uses agree on; the finding is then spelled with the screen's own word, because told *"writes `<*Grid>` without `density`"* a reader goes looking for a component called `*Grid`. Presence and value are two claims: `data-*` and `key` are filtered where a *value* is decided and counted where *presence* is, since the value of a test id is an artefact of the page and writing one at all is a convention — 190 of 209 usages.

**Two rules govern what a deterministic check may say.** It fires only on something certain — a raw literal, a name the project has written a prohibition about. And a rule only speaks about the files it is about: rules are scoped by the same retrieval Tier 2 uses, because a finding citing a rule that does not apply teaches people to stop reading them.

Still deferred and not to be pulled forward: theme `defaultProps` / `styleOverrides` resolution. Duplicate-shape detection was deferred and is now built, as `uic shapes` — a separate read-only command, never part of the per-file gate, because from an AST a propagated mistake and a shared pattern look identical.

**Nothing here is MUI-specific except where it is named as such.** The resolution check treats the outermost layer as "an external UI library". The prop check takes its allowed set from an injected source of truth and never invents one, so it is name-agnostic too. The only MUI-shaped things left are the `sx` semantics in `src/checks/style.ts` — `sx` is spelled the same by MUI, Chakra and Theme UI, and its spacing keys are read as MUI reads them — and the deferred theme resolution, which would be MUI first. Class-based systems (Tailwind, CSS modules, styled-components) are out of reach of a per-file AST check by construction; say so rather than implying coverage.

**What a screen *is* differs by framework, and that is not a vendor question** (`src/sources/pair.ts`). **The two halves of a pair are parsed by different things and fail differently**: the template by the tolerant HTML parser, the `.component.ts` by Babel — which had no decorators plugin until one was added, so every decorated class was a syntax error and everything read from it was empty, the inventory included. A `uic pattern` that answers on the `.html` while `uic place` on the `.ts` says nothing is that shape. React, Solid and Qwik: one file. Vue and Svelte: one SFC. **Angular: a pair** — `foo.component.ts` carries the identity, the imports and the wiring, `foo.component.html` carries the markup, and neither is a screen alone. Reading them as two unrelated candidates left every command above the layer check silent on a real Angular monorepo of 179 components. Either half resolves to the same screen; a `@Component` with neither `templateUrl` nor `template` is not a screen.

**The plugin must work for any organization, and for a single-package app as well as a monorepo.** Structure is detected, never required as config. Never design around one particular monorepo.

**A repository where detection finds nothing at all still gets every check that does not need a package** — style literals, emoji-as-icon, stated page rules, curated substitutions. Only three read a chain: imports, deprecated usage, and the layer half of substitutions. Do not reintroduce a gate that skips a file because no package was found; that is how a fresh install ends up silent on the day somebody is deciding whether the plugin does anything.

**That fact is only useful if somebody can see it, and `skills/reach` is what makes it visible** — **and since #37 the CLI says it for itself** (`src/core/coverage.ts`). A command answering with empty output and exit 0 makes *clean* and *blind* the same answer, which is how 400 screen files were reported as success on a repository where nothing had been looked at. `uic check` that finds nothing now says what it read, which checks could not run and why, and — the case that is legitimately silent — that it reads `sx` and inline `style` objects only, so a project styling in class strings or CSS template literals is told it is out of reach by construction rather than handed a clean report. It is paid for only where there are no findings. `uic inventory` on a file no package owns says so instead of printing nothing, and a `check` where **not one** file could be read exits non-zero — the answer `diff` already gives where none of its paths was a screen. A project no package was detected in is deliberately *not* that case: every check needing no chain ran on every file, and failing those would be the gate this file forbids two paragraphs above. A user cannot otherwise tell *"my project is clean"* from *"this tool is blind here"* — every command answers for itself, and each one's silence looks like success. The skill reports three answers and only three, level by level: it works and here is what it read; it is quiet because the project has stated nothing, which is the design; or it is blind here, and here is why. No score, no grade, and never a level called working because it produced no findings.

Detection has two mechanisms and needs either one (`src/layers/detect.ts`, `src/layers/tsconfig.ts`):

- **manifests** — `pnpm-workspace.yaml` / `package.json` `workspaces` for the package set, each package's `dependencies` for the edges
- **`tsconfig` path aliases** — for workspaces whose libraries have no `package.json`, which is the normal Nx shape. Nothing declares dependencies there, so the edges are derived from the imports in the source

A declared package is taken at its word; aliases only fill in what no manifest describes, so a repository that already worked keeps its cost and behaviour. The derived graph is cached (`src/layers/cache.ts`) against the alias file's mtime, because deriving it parses every source file. That accepts a bounded staleness — a brand-new edge between two existing libraries is unseen until `uic scan` — and the failure direction is a missed finding, never an invented one.

**A first run on an unseen repository is an acceptance test now, and it is committed** (#39, `scripts/first-run.mjs`, `npm run first-run <paths>`). The problem it exists for, stated once: installed on a repository it had not been developed against, this tool answered **nothing, everywhere, and called it success** — one binary, two real React monorepos, the same day; 132 findings and exit 1 on one, and on the other 0 findings, exit 0, an empty `--list` and an empty inventory over 400 screen files. The second repository was not cleaner. Nothing in it was ever looked at. Five issues closed the particular holes (#31, #32, #35, #36, #37) and closing them without this would leave the same hole for the next repository with a convention nobody anticipated: **the test is the deliverable and the fixes are how it goes green.**

It asserts one thing over every command the binary admits to having — read off the usage line, so a command added and not exercised fails the harness rather than escaping it — on a repository with nothing configured and nothing written down: **no command may answer with empty output and exit 0.** Each answer is one of `answered`, `stated`, `refused` or `no file`, and `silent` is the only failure. It has no opinion of its own about what counts as blind; `src/core/coverage.ts` is that opinion and a second copy would be the duplicate this file forbids.

**A committed harness and a run against real repositories are two artefacts, and conflating them is the same defect one level out.** So it **takes repositories as arguments and fails when given none** — a first-run acceptance test that goes green on a clone with no repository present is *nothing, everywhere, called success*. `tests/gate/first-run.test.ts` proves the harness works and proves nothing about whether the tool is blind anywhere; that claim comes from the run below. Per-file commands are asked about **five** files rather than one, because pointed at a single wiring file a real app answered *nothing routes it* and *fewer than three screens of this kind* — both true of that file and neither a fact about the tool. Choosing better is not available: guessing which file is a screen is what deleting `archetype.ts` settled.

**The run, 2026-09-11, three repositories and three conventions, at 0.14.101: no level silent on any of them.** A single-package Ionic React app with JSX `<Route>` elements rather than a route-object table — 21 screen files, `check` answered with findings and exit 1, and `place` and `pattern` answered for **5 of 5** pages, reading `/practice` out of the JSX and deriving `IonPage / IonHeader / IonContent` from the project's own code, a vocabulary nothing here was told about. A 461-package monorepo — `place` *stated* for 5 of 5, because routes there are registered through a route-ref extension and not a path table, which is the blind answer said out loud rather than a clean one; `pattern` answered for 2 of 5, `group` and `shapes` answered, `check` found 36. And this repository, which has no screens application in it at all — `check` stated its coverage over 21 files, `review` stated that nothing is written down, and `pattern` still answered for 3 of 5. The convention the original measurement turned on — route paths as members of one enum — is **not available publicly**, which is the same refusal seventeen candidate repositories already returned by design; #36 closed it and no public repository proves it.

**Whether the agent writes a better screen is not measured yet, and the half that can be is committed** (#34, `scripts/bench.mjs`, `bench/tasks.json`, `npm run bench`). The claim this project rests on is one sentence — *a screen written with the pattern in front of the agent matches its neighbours, and one written without it drifts, and by file twenty the difference is the whole problem* — and everything measured so far is about the tool's own insides: 37 ms cold, 108 of 117 routes, 13 props agreed by 6 of 6. Those say the fact supplier is accurate. None of them says the agent wrote a better screen.

What is committed is the arithmetic half: given two arms' screens and the pattern for their kind, **conformance** (mean deviations per screen) and **the drift curve** (the first third against the last third, per position). It scores through `uic diff --contract --json` — `patternDeviations` and nothing else, for the reason every adapter here obeys. Two of the four numbers the issue asks for are **not obtainable from files on disk at all**: cost in tokens and wall clock has nothing to record when no agent ran, and the false-finding rate is defined as findings a judge rules wrong, which is a judgement. **So the verdict does not exist yet, and no number from this goes in `README.md` until it does** — the headline belongs there only if it is real and dated.

Two guards carry the meaning. **The pattern must be committed before the arms were written**, enforced by reading git: a pattern with uncommitted changes, or one git has never seen, is refused, because a run scored against something authored from its own output measures nothing and still looks like a result. And **arms of different lengths are two experiments**, refused rather than compared, with a batch below the stated minimum of 15 told that a curve that short cannot bend. `tests/gate/bench.test.ts` proves the scorer against a *planted* curve — an arm built to degrade with position and an arm built to match — and proves nothing whatever about the claim, because no agent wrote any of those files.

**The first dry runs of that benchmark found two things worth more than the numbers they produced, and both are against this project's own claims.** Recorded because a finding beats a claim, and because both were missed in review and caught by running it.

**The drift claim did not reproduce.** *By file twenty the difference is the whole problem* is the sentence the whole benchmark was built to test, and over 18 screens written in one session the arm without the pattern was **flat** — 0.33 deviations per screen in the first third and 0.33 in the last. Whatever it got wrong, it did not accumulate with position. Either 18 screens in one session is too short to bend, or the effect is not positional; the benchmark as designed could not tell those apart, and neither can this sentence. What is withdrawn is the confidence, not the claim. **Two things changed so the next run can tell them apart** (#63): the task set runs to 40 rather than 18, with `minimumBatch` flagged as the guess it is — 15 came out of an issue body and nothing measured where an effect would begin — and the report carries a **second axis**, how many deviation kinds each screen introduced that no earlier screen had. *Consistently missing one prop* and *inventing a new mistake every few screens* are the same mean and the same flat count curve, and only the second is drift; on the partial run every kind was established by position 4 and nothing new appeared after, which reads as uniform rather than drifting. **The answer still needs the runs**, and what hangs on it is larger than the benchmark: `skills/rollout`'s whole shape assumes attention thinning within a session.

**The baseline is much stronger than assumed, and a mean hid what the difference actually was.** With no pattern and only the neighbouring screens to read, that arm used the correct holder on 18 of 18 and wrote the title, the breadcrumb and the test-id prop on 18 of 18; every one of its deviations was the *same single boolean prop*. A conformance mean of 0.39 against 0 does not convey that, so the report now lists **what** was wrong and on how many screens — one prop missing on seven screens and seven props missing on one screen are the same mean and are not the same result.

**And the ON arm's score was worthless, by construction** (#57). It had been told to run `uic diff --contract` on each file and fix what it reported — the scorer's own command against the scorer's own pattern — so it was handed the metric and told to zero it. An ON score above zero could only have meant the agent ignored an instruction. The treatment is now that the pattern is *readable* and nothing more, which is what the plugin does before a write; benchmarking the per-edit gate is a different experiment needing a metric the arm was not told to optimise.

**Fixtures here have never caught a real defect.** Twenty-three real bugs now, twenty-three times the suite was green — fifteen of them in a single day at 574 to 607 passing tests, including a contract check dead on every template dialect, a CI line that checked nothing and exited 0, and four security findings over a scope already argued to be safe. One earlier Tier 2 was dead for every installed user while all 307 tests passed, because the suite runs from the clone, where `npm install` has run. Every fixture is written by whoever wrote the rule and encodes the same assumption, so a green run is not evidence. Validate against a real repository at real scale, break things on purpose — and for anything user-facing, run the **shipped artifact**: copy `bin/uic.mjs` alone into an empty directory and use it there.

**Three guards now enforce what review kept missing, and each has a limit worth knowing.**

- `tests/cli/names.test.ts` — parses every module and fails on a `uic <command>` or `ui-consistency:<skill>` in a **string literal** that does not exist. Literals, not file text, so a comment may still record that something was deleted.
- `tests/core/duplicates.test.ts` — hashes function **bodies**, so it catches a copy renamed. It cannot see a copied *algorithm* inlined in a larger function body, which is how a fourth copy of `walk` survives in `checks/style.ts`.
- `noUnusedLocals` — locals and imports only. Parameters are exempt on purpose: an unused parameter is often a signature kept deliberately.
- The **no-hardcoded-vocabulary** rule above is enforced only where a *finding* can come from, and that is narrower than it sounds. `archetype.ts` decided what kind of screen a file was from `Dialog|Modal|Drawer|Popover|Sheet`, `Table|DataGrid|DataTable|List|VirtualList` and a third list like it, and no guard reached it — an archetype is not a finding. It said *"not readable from the code"* about 12 of 13 real pages, because a project's grids are called `CustomerInvoicesGrid`. Deleted; the kind is the **holder** now, which is structural. Anything that is not a finding but still speaks about the project is outside the guard and ~~has to be watched by hand~~ **is watched by `tests/private-names.test.ts`**, which fails on any private name in a tracked file's path or contents, against a list kept outside the repository — a committed denylist being itself the leak. The rule it enforces is in `.claude/rules/uic-docs.md`: evidence from a private repository keeps its numbers and loses its names. Watching by hand was the plan for a month and it did not work: one change carried five names from its own issue body into `src/`, the tests and this file.

**The knowledge directory is `.ui-consistency/`, and `.claude/ui-consistency/` is still read as a fallback and reported when used** (`src/knowledge/paths.ts`). The old path is load-bearing, not vestigial — a silent fallback would leave everybody on it forever, and dropping it would lose files already in people's repositories.

**The log is not free of the project's code, and must never be described as if it were.** A finding quotes what it found, so `message` carries literals out of the file, and `contract-*.json` beside it carries prop values and class strings verbatim. The old "no source code, ever" was a claim about the *keys* dressed as a claim about the contents. What is true and worth keeping true: five fields and no sixth, values quoted through `quoted()` at one line and eighty characters, and a directory that is owner-only and refused if anything else owns the name. What protects it is the location, not the format.

## Monetization

The plugin is free. Skills and hooks are copyable text and the plugin marketplace has no payment mechanism. Do not add licence checks, telemetry or paywalls to it. If a paid layer is ever built it is the team layer around the CLI, not the plugin.
